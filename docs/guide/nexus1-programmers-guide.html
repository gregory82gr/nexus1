How to read this guide

This guide is written by one programmer for another. It assumes you are comfortable with C#/.NET, SQL Server and a terminal, and that you want to know how the thing actually works — not a marketing tour.

Three conventions run throughout:

  • VERIFIED marks a statement that was checked against the live system or the repository while this guide was written (the evidence is named next to it).
  • GAP marks something that is deliberately not built, only partially built, or known to be wrong in the repo's own docs. The project's standing rule is that a gap gets named, never hidden (Section 5 explains why).
  • File paths are repo-relative. ADR numbers refer to docs/adr/ADR-NNN-*.md; evidence reports live in artifacts/evidence/.

Three corrections to the brief this guide was written from, made because the repository disagreed and the repository wins:

  • There are 17 bounded contexts (one per Schema Atlas sector). Nexus1.ModularRuntime composes 16 of them; the 17th, RootCause, runs in Nexus1.RootCause.Host. The BFF surfaces all 17 (16 in-process, RootCause over HTTP).
  • The RootCause/RAG phase is 17 commits since ADR-032, not sixteen: 15 feature slices plus 2 small corrective commits. All 17 are listed in §2.8.
  • The provisioning runbook's migration command (--startup-project src/Hosts/Nexus1.RootCause.Host) did not work — the hosts do not reference Microsoft.EntityFrameworkCore.Design. The working form (§6.3) was verified on this machine, and the runbook was corrected in the same commit as this guide, together with two other runbook errors found while writing it (step order, stale seed counts).

1Project topology

NEXUS-1 is a hybrid: a modular monolith that keeps most of the domain in one process, with exactly one bounded context — RootCause — extracted to its own independently deployed host. The book series argues for earning each extraction; this repository extracted only the one the architecture decision records justify.

1.1 The shape in one picture

Read the picture as three facts:

  1. Most of the domain is one deployable. Sixteen contexts share the Nexus1.ModularRuntime process. ReactorFleet produces simulated telemetry that AlarmManagement consumes in-process to detect alarm floods (ADR-001-amend).
  2. RootCause is the one extraction. Nexus1.RootCause.Host owns RootCauseDb outright, consumes alarm-management.alarm-flood-detected.v1 from the broker, publishes its own events through a transactional outbox, and hosts the diagnosis (RAG) pipeline.
  3. The console talks to exactly one origin. Nexus1.Bff composes the in-process contexts' Application layers directly and reaches RootCause only through an HTTP proxy. The browser never sees RootCause.Host.

1.3 Solution layout and the dependency law

The layout is context-first (ADR-002, from From Services to Runtime Ch. 4): project-per-context-per-layer, never folders named "API/Worker/Database".

The dependency law is enforced by Nexus1.ArchitectureTests, which parses every .csproj's <ProjectReference> graph (not compiled IL) and fails the test gate on violation:

  • Inside a context, dependencies point inward: Infrastructure → Application → Domain.
  • Across contexts, a project may reference only another context's Nexus1.Contracts.* project — never its Domain, Application or Infrastructure.
  • Domain never references transport, persistence, hosts or contracts (domain events are not integration events).
  • Hosts are composition roots only.
  • Served-model packages (Semantic Kernel, the Ollama connector) may appear only in Nexus1.RootCause.Explain (ADR-032/033).
  • No passwords in any appsettings*.json under src/ (ADR-044).

1.4 The messaging backbone

Integration events travel through RabbitMQ with a transactional outbox on the producer side and an inbox (idempotent consumption) on the consumer side (ADR-008), plus retry with backoff and dead-lettering (ADR-009). All publishes go to the durable topic exchange nexus.events; dead letters go to nexus.dead. Queues are quorum queues; dead-lettering is applied as a broker policy through the management API at consumer start.

Startup behaviour (ADR-044). Both hosts that talk to the broker now start and retry when it is unreachable: the connection is made by a background loop with backoff (1 s doubling to a 30 s cap), and each consumer's start sequence is retried through the shared ConsumerStartup helper. Before ADR-044, a missing broker crashed ModularRuntime (~9.7 s) and RootCause.Host (~16 s) with an unhandled BrokerUnreachableException. Readiness never depends on the broker — no HTTP route uses it.

1.5 The BFF and the Angular console

console/nexus-console is an Angular 18 application (Jest unit/component tests, Playwright end-to-end tests). Every API client targets a single constant, BFF_BASE_URL = 'http://localhost:5103'. The BFF enables CORS only in the Development environment and only for http://localhost:4200.

For RootCause, the BFF adds two thin proxies — POST /api/v1/root-cause/incidents/{id}/diagnoses (ADR-035) and GET …/{id}/graph (ADR-036) — that relay the host's status, body and content type verbatim. If RootCause.Host itself cannot be reached, the BFF returns 502; if the host ran but a dependency of its pipeline failed, the host's own 503 is relayed. That distinction is deliberate and diagnostic.

The RootCause screens (Ch. 29) are /rcgraph (Root Cause Graph: verdict, ranked candidates, citations, audit hash, and the drawn fault tree) and /incident (Incident Analysis: the top cause). Both read one shared RootCauseService, so one diagnosis run feeds both — a property the live @slow Playwright test asserts end to end.

1.7 Topology gaps, named

  • No container images for the .NET hosts. Only the console has a Dockerfile. A Kubernetes-readiness investigation (before ADR-044) found the health endpoints are now correct, but no image, manifests or non-LocalDB database target exist.
  • No authentication/authorization on any HTTP surface beyond the development status quo.
  • The BFF has no observability (no tracing/metrics); edge metrics such as nexus1.edge.requests are deferred (ADR-007/030/038).
  • Two test projects are empty shells: Nexus1.Contracts.ContractTests and Nexus1.DistributedSlice.EndToEndTests contain no .cs files and report "No test is available".
  • The console's README is the Angular CLI boilerplate (it mentions Karma; the project uses Jest and Playwright). The real E2E instructions are in console/nexus-console/e2e/README.md.

2How the RAG was built, and why

2.1 The purpose, plainly

RootCause's diagnosis pipeline is a deterministic, grounded, auditable root-cause engine in which a language model only narrates a decision it never makes itself.

When an alarm flood hits, the engine decides which component started it by walking an engineered causal graph, checks that decision against the physical telemetry, and grounds it in a retrieved corpus. Only then is a small local model allowed to explain the already-made decision — in a strict output schema, citing only passages that were actually retrieved, naming only components that exist. Anything that fails a gate produces a named abstention instead of a verdict. Every outcome, verdict or abstention, is sealed into a SHA-256 hash chain that anyone can recompute (Section 3).

The design inverts the usual "ask the LLM what happened" RAG. Here the LLM is the least trusted component in the system, and the architecture is built so that it structurally cannot change the answer.

2.2 Where it started: From Flood to Cause

The RAG phase began with a close reading of From Flood to Cause, a NEXUS-1 companion book that describes the "One-Truth Pipeline": a deterministic engine decides, a served language model explains, and ten anti-hallucination controls (H1–H10) make confident fabrication structurally hard. Its Chapters 8–9 give the C#/SQL production form, Appendix C the grounding schema, and Figure 2.1 the worked incident EVT-2026-0418 as a causal fault-propagation graph with delay windows. Chapter 10 works three case studies: 0418 (a cascade), 0419 (a measurement artefact) and 0420 (a QA escape).

Two constraints shaped everything that followed (ADR-032):

  • The book is not in the repository. It is outside the project's seven-source authority list, and ADR-029 purged licensed source PDFs from the repo and its history. Every value the book supplies is therefore pinned — in the ADRs and in GroundingSeed — so the implementation traces to a recorded decision rather than to a PDF the repo does not carry. Figure 2.1's delay windows were re-derived from the book (pdftotext -table) and cross-checked arithmetically.
  • The book targets SQL Server 2025 preview features (VECTOR(1024), VECTOR_DISTANCE, AI_GENERATE_EMBEDDINGS). The available database is SQL Server 2016 (LocalDB 13.0 SP1). So cosine similarity is computed in C#, and embeddings are stored as JSON in Corpus.EmbeddingJson.

2.3 The fixed-incident-first decision

Instead of building a general question-answering assistant, the project built one fixed incident end to end — EVT-2026-0418 — as a walking skeleton, and only then added depth. The reasoning, recorded across ADR-032 to ADR-034:

  • A single known incident has a known right answer. The book's own figure says FV-104 explains 11 of 14 alarms. If the engine computes 11/14 from seeded alarm counts, that is evidence; if it merely prints it, it is theatre.
  • It exposes every seam at once. Graph walk, telemetry corroboration, retrieval, generation, validation and sealing all have to exist for one incident to go through. Nothing can hide behind "later".
  • It refuses premature generality. A second incident (0419) was added only after the first was proven over HTTP, in the browser and in a live E2E test. The third (0420) is deliberately not solvable by the engine, and the repo says so.
  • It gives the generation stage nowhere to hide. ADR-032 shipped the deterministic half with the model stage visibly unbuilt — no stub, no simulated narrative — until the hardware for a local model existed (ADR-033).

2.4 The One-Truth Pipeline

FixedIncidentDiagnosisRunner (Application layer, LLM-free) composes six stages behind interfaces. Each stage either passes the run forward or ends it with a named abstention.

What each stage actually does, in the code as it stands (ADR-032, 037, 042, 043):

  1. Graph walk (EfGraphWalker). Candidates are every component that is alarmed in the flood or is the source of an authored edge. Each candidate's explanation is the set of alarmed nodes reachable over backbone and artefact edges; learned edges are subordinate and rejected edges are never walked. Ranking is a greedy set cover (most not-yet-explained alarms first; ties by earlier historian onset, then lower ComponentId). Weight is an attribution share. Roles are structural: origin, downstream, parallel, contributing, independent, ruled-out. Nothing is read from seeded "answer" fields (ADR-042).
  2. Corroborate (EfTelemetryCorroborator). Cascade mode: every backbone edge on the origin's forward path must fit its delay window against historian onsets. Artefact mode: coupled channels deflect together, and independent witnesses must stay flat — silence is the evidence. Both modes then apply the unexplained-precursor rule: an alarmed component the origin does not reach, with a strictly earlier onset, means the graph is probably missing a coupling, so the run abstains (ADR-043).
  3. Retrieve (EfRetriever). Exact lexical tag match plus a C# cosine path over nomic-embed-text embeddings with an H2 relevance floor of 0.5. The corpus is scoped by unit, so incidents never ground on each other's passages.
  4. Explain (SemanticKernelExplainer in Nexus1.RootCause.Explain). One chat call to the pinned local model nexus-dslm, parsed into a strict JSON schema. A refusal or an unparseable reply is an abstention — never salvaged.
  5. Validate (RegistryAntiHallucinationValidator). H3: every named entity must exist in the component registry. H4: every claim must cite a passage that was actually retrieved.
  6. Seal (Sha256AuditChainWriter). The run's inputs, conclusion, candidates, citations and validated answer are serialized to JSON and appended to RootCause.Audit, where Hash = SHA-256(PrevHash + Payload) from a 64-zero genesis.

2.6 Semantic Kernel, on a short leash

The model stage uses Microsoft Semantic Kernel 1.50.0 with the Ollama connector (1.50.0-alpha) — pinned below the latest release because 1.80.x pulls the .NET 10 Microsoft.Extensions.* wave into a .NET 8 solution (NU1605). The constraints are the point:

  • FunctionChoiceBehavior.None() — no planner, no automatic tool calling. The model cannot call functions, query anything or decide which steps to run.
  • Temperature 0, seed 42, one call (GetChatMessageContentAsync), with the determinism parameters pinned in the Modelfile rather than left to the caller.
  • The model is told the answer. The prompt carries the origin the engine already chose; Modelfile rule 1 says cause must be exactly that tag, and rule 2 restricts entities to that one tag. The model's job is to explain, not to decide.
  • No database dependency. SemanticKernelExplainer receives passages and returns a draft, so it structurally cannot read or write the store.
  • Air-gapped by configuration. Ollama binds 127.0.0.1. During ~70 s of continuous inference, zero non-loopback connections were observed from any Ollama process (ADR-033 evidence).
  • One project holds it all. An architecture test fails the build if a served-model package appears anywhere except Nexus1.RootCause.Explain.

2.9 Where the engine stands today

Live on 2026-09-25 while writing this guide VERIFIED: a diagnosis of EVT-2026-0418 returned FV-104 (origin, attribution weight 0.79, coverage 11/14) with RCP-1B parallel (0.14), BUS-2A contributing (0.07), six downstream symptoms and FT-7 ruled out, citing the book's Ch.1-2 and Ch.2 passages. EVT-2026-0419 returned BKR-2A (weight 1.00) with FT-9, LT-3 and PT-7 downstream and LOF-1 ruled out. EVT-2026-0420 returned 404 unknown incident.

Named gaps in the RAG as of this commit

  • True retrieval_recall (Appendix J) is not measured. Three incidents are far too small a labelled set; grounding_hit is a proxy (ADR-038, 041).
  • No CauseTag-vs-origin check. A draft naming a registered, retrieved but wrong component (e.g. RCP-1B for 0418) would pass H3/H4; the H9 leading-question trap is skipped by name until that engine slice exists.
  • No free-form question interface. The route takes an incident id; the "DSLM advisory" in the console's AI Diagnostics screen is labelled "not running in this build".
  • Audit and Compliance do not consume RootCauseCaseInconclusiveV1. They bind only the verdict key, so they safely never receive it. The extension is the named follow-on of ADR-040.
  • Mismatch classes the precursor rule cannot catch (ADR-043): a silent true cause, a spurious edge whose timing fits, a missing downstream edge; and a standing alarm with an early onset would cause a false abstention.
  • 0418's delay windows are exact points (min = max), so one second of real jitter would make it abstain. Recorded, not changed.
  • The weights are attribution shares, not probabilities. The console still labels them "Illustrative weight" / "Illustrative confidence" — a wording mismatch left from before ADR-042, named for a UI slice.

3Verify the claims yourself

This project's standing rule is evidence over assertion. This section applies that rule to the guide itself: instead of trusting that the audit chain works, you run one fixed incident and watch the hash in the HTTP response match the newest row in RootCause.Audit — then recompute it yourself, with no project code involved.

Everything below was run exactly as written on 2026-09-25 against this commit. The sample outputs are from that run. Your hashes will differ — they depend on your chain's history and on the model's narration — but the relationships must hold.

3.1 What you need running

Only three things: LocalDB with RootCauseDb migrated and provisioned, Ollama with nexus-dslm and nomic-embed-text, and Nexus1.RootCause.Host. The row's Hash is the auditHash you just received. Its PrevHash is the previous row's hash — that is the chain.

3.4 Recompute it yourself — the whole chain

Matching two strings proves the route returned what it stored. It does not prove the stored hash is honest. So recompute it: the formula is lowercase hex SHA-256(UTF-8(PrevHash + Payload)), starting from sixty-four zeros (Sha256AuditChainWriter.ComputeHash). The companion script docs/guide/verify-audit-chain.ps1 does that for every row. It uses only Windows PowerShell's built-in System.Data.SqlClient and your own Windows login — no project assemblies, no SQL-login secrets.

.\docs\guide\verify-audit-chain.ps1 -ExpectedLatestHash 1bd5bcfbb3ba404c1cf068c2c60e0f0115da162b91fa7c170f69a2dc2df5c646
Rows checked: 41   broken links/hashes: 0
Newest row:   Seq 41 at 2026-09-25 09:03:35Z
  stored     Hash = 1bd5bcfbb3ba404c1cf068c2c60e0f0115da162b91fa7c170f69a2dc2df5c646
  recomputed Hash = 1bd5bcfbb3ba404c1cf068c2c60e0f0115da162b91fa7c170f69a2dc2df5c646
  payload (first 160 chars): {"IncidentId":"EVT-2026-0418","Verdict":"FV-104","AbstainReason":null,…
HTTP auditHash matches newest row: YES
CHAIN INTACT

The heart of the script is four lines — short enough to audit before you run it:

function Get-ChainHash([string]$prev, [string]$payload) {
    $bytes = [System.Text.Encoding]::UTF8.GetBytes($prev + $payload)
    ($sha.ComputeHash($bytes) | ForEach-Object { $_.ToString("x2") }) -join ""
}   # each row: PrevHash == previous row's Hash, and Hash == Get-ChainHash(PrevHash, Payload)

Now try to break it. In a throwaway copy of the database, edit one character of any row's Payload and rerun the script: that row's recomputed hash no longer matches, and the tampering is reported at its exact Seq. That is what "tamper-evident" means here — not tamper-proof, but impossible to alter silently.

4Troubleshooting known setup friction

Every item here happened on the project's own machine — a Windows 10 laptop with an Intel i5-3340M, 16 GB of RAM, no GPU and no administrator rights — and is recorded in its runbooks or evidence reports.

4.1 SQL Server LocalDB

  • The instance name is (localdb)\mssqllocaldb everywhere. It is SQL Server 2016 (13.0 SP1) on this machine — which is why the project computes cosine similarity in C# instead of using SQL Server 2025's vector features (ADR-032).
  • Migrations must run before the SQL logins are created. The login scripts do USE AlarmManagementDb, USE RootCauseDb and so on, and those databases only exist once migrations have created them. Earlier revisions of the provisioning runbook listed the logins first; it now puts migrations first, and both login runbooks state the prerequisite (§6.3).
  • Use the Infrastructure project as the EF startup project. dotnet ef … --startup-project src/Hosts/… fails with "doesn't reference Microsoft.EntityFrameworkCore.Design". Every *.Infrastructure project references the design package and carries its own design-time factory.
  • Pending migrations make readiness 503. DbContextHealthCheck<T> checks connectivity and that the context's migrations are applied (ADR-018), using that context's own history table (__EFMigrationsHistory_<Context>). A "reachable but missing N migration(s)" message means migrations were not run — or, as ADR-044 found, that a context was configured with the wrong history-table name.
  • sqlcmd on this box: the provisioning runbook notes that -i needs an absolute Windows path. The developer's Windows login is sysadmin on LocalDB; use -E (trusted) for administration and the scoped logins only to test their permissions.
  • Transient LocalDB command timeouts appear under heavy concurrent load. See §4.4 — the fix is less concurrency, not bigger timeouts.

4.2 RabbitMQ

  • Use Erlang/OTP 27, not the latest. RabbitMQ 4.3.4 failed to boot on OTP 29.0.5 with BOOT FAILED {incompatible_feature_flags, …}. The portable OTP 27.3.4.16 works, pointed at through ERLANG_HOME (docs/runbooks/local-rabbitmq.md).
  • The management plugin is required, on port 15672. Consumers apply their dead-letter policy through the management HTTP API at startup, and the port is hard-coded (RabbitMqOptions.ManagementPort = 15672, not read from configuration). Enable it with rabbitmq-plugins enable rabbitmq_management.
  • guest/guest works only over loopback (RabbitMQ's default). That is fine locally and will fail from another machine or a container.
  • New shells need the environment variables. ERLANG_HOME and RABBITMQ_BASE are set at user level; an already-open shell will not see them.
  • If the broker is down, the hosts still start (ADR-044). Look for RabbitMQ unreachable … retrying in … in the log, and Connected to RabbitMQ … on attempt N once it appears. A credentials problem is logged distinctly: "RabbitMQ rejected the configured credentials …". The outbox relay logs an error every 250 ms while the broker is down — known noise, not fixed.

4.3 Ollama and the 100–150 s cold start

  • A cold call takes about 93–150 s on CPU (model load plus first generation); warm calls take roughly 20–70 s. On 2026-09-25 a cold 0418 call took 105 s and a warm 0419 call 71 s.
  • Timeouts are layered on purpose: the host's chat call allows 150 s (Ollama:RequestTimeoutSeconds), the BFF's hop 180 s, and the live E2E test 180 s. The host fails first, so a slow model surfaces as the host's own 503, not a BFF 502.
  • Make cold starts rare: set OLLAMA_KEEP_ALIVE (e.g. 30m, or -1 for indefinitely) on the Ollama process. It does not remove the first cold call after Ollama restarts.
  • Readiness ollama … model(s) not installed means the server answers but nexus-dslm or nomic-embed-text is missing: build or pull it (§6.5). A Healthy ollama check does not mean the model is loaded.
  • "Still missing an embedding" after provisioning means Ollama or nomic-embed-text was unavailable. Lexical retrieval still works, and the semantic path wakes up after you rerun -- provision.
  • Ollama updates itself. ADR-033 pinned Ollama 0.34.2; this machine now runs 0.34.3. The model is pinned by its base blob digest (sha256:5ee4f07c…), which is what reproducibility rests on.

4.4 Memory contention on modest machines

A 3B model needs about 2 GB of contiguous RAM, and each test assembly plus LocalDB adds more. The project hit this for real:

The H9 slice's parallel-run incident (2026-09-24-h9-evaluation-harness-core.md). dotnet test Nexus1.Runtime.sln ran all assemblies at once: 34 passed, 3 failed. EmergencyPreparedness and ReinforcementLearning component tests hit SqlException: Execution Timeout Expired, and two live Ollama tests got HTTP 500 — Ollama's own server.log read "failed to allocate CPU buffer of size 1923946496 … unable to allocate CPU buffer". Every assembly passed when rerun in isolation. The timed-out runs also left three test databases behind, which were dropped by hand.

  • Run test assemblies one at a time when the live model tier is enabled. Every slice since H9 does exactly that for its regression gate.
  • Do not run the full E2E stack alongside a full test run. Start the stack after the tests finish.
  • Leftover *ComponentTests_<guid> databases after an interrupted run can be listed with SELECT name FROM sys.databases WHERE name LIKE '%Tests[_]%' and dropped once you have confirmed they are yours.
  • An earlier observability campaign recorded the same class of problem: a transient LocalDB command timeout under heavy concurrent polling (2026-08-16-observability-final-chain-proof.md).

4.5 Observability stack

  • Prometheus 3.x keeps dotted OpenTelemetry names (nexus1.diagnosis.*), which Grafana 10 cannot query. docs/observability/prometheus.yml therefore sets metric_name_validation_scheme: legacy, giving the underscore names the dashboard uses. If you changed the scheme after scraping, wipe the TSDB directory.
  • The or vector(0) trap: on a labelled metric it returns the real series and a phantom empty-label 0, so a stat panel shows two numbers. The committed dashboard wraps these in sum(… or vector(0)) (ADR-038 evidence).
  • The dashboard provider path is absolute (grafana/provisioning/dashboards/nexus1.yml); adjust it to your checkout.

4.6 Hosts, BFF and console

  • "Missing ConnectionStrings:… configuration" at startup means that host's User Secrets are not set, or the host is not running in the Development environment (User Secrets load only there). See §6.4.
  • The BFF returns 502 on a RootCause route when RootCause.Host is unreachable; a relayed 503 means the host ran but a dependency (Ollama, a database) failed. Both bodies carry a traceId to search for in the log.
  • The console's calls are blocked by CORS unless the BFF runs in Development and the console is on exactly http://localhost:4200.
  • Playwright cannot find @playwright/test when launched from some shells. Setting NODE_PATH to console/nexus-console/node_modules fixed it here.
  • The BFF's Overview endpoint resolves several contexts at once and fails as a whole if one is not composed. When using BffContexts__Enabled__N subsets, include the contexts the screen needs (console/nexus-console/e2e/README.md).

5The honest-gap discipline, as philosophy

"Nothing claims to exist that does not. A diagram, a 'done' checkbox, or a status message is valid only when it matches the repository, the contracts, the data ownership, the tests, and the observable runtime behavior." — the project's standing rule (CLAUDE.md).

It would be easy to read that as house style. It is closer to a load-bearing requirement, for a reason specific to what this repository is. NEXUS-1 is a public teaching reference backing a book series — cloned, in the project owner's words, by more than two hundred readers. Every one of them will lift patterns out of it: a readiness check, a retry loop, a way of wiring a local model. A reference implementation that overstates what it does teaches the overstatement along with the code. So every claim has to be checkable, and every gap has to be named where a reader will trip over it — not tucked into a backlog.

Three examples from this repository's own history show what that means in practice.

The narration is not deterministic, and the project says so

The book's H6 control asks for determinism. Temperature 0 and a fixed seed look deterministic, and it would have been easy to assert that. When ADR-033 measured it, the engine's verdict was identical run after run — but the model's narration was not byte-identical, because multi-threaded float reductions on a CPU vary in order. The project recorded exactly that: the decision is the deterministic guarantee, the prose is not. The consequence is visible in Section 3: two runs of the same incident seal different hashes over the same verdict, and nobody is surprised, because it was never claimed otherwise.

Reachable is not warm

ADR-044's Ollama readiness check calls /api/tags. A green result means the server answers and both models are installed — and nothing more, because /api/tags never loads a model. The easy thing would have been a check named "ollama-ready" that let everyone assume the model was hot. Instead the check's own Healthy description says it is not a warmth check, and the slice proved the distinction live: with the model unloaded (ollama ps empty before and after), readiness stayed 200. A reader copying the pattern copies the caveat with it.

A detection rule that ships with a map of its blind spots

ADR-043 added a rule that makes the engine abstain when the evidence says its causal graph is incomplete. The rule is genuinely useful, and the ADR spends as much space on what it cannot do: a silent true cause, a spurious edge whose timing happens to fit, a missing downstream edge, and the rule's own cost — a standing alarm could trigger a false abstention. The same slice also refused an easier win: its test of the old engine "passed" by abstaining with no grounding, only because the fixture had no corpus. The evidence names that as accidental rather than counting it as detection.

Why gaps are named in the artifact itself

Naming a gap costs a sentence. Hiding one costs every reader who builds on the unstated assumption. That is why the console labels its advisory panel "not running in this build"; why EVT-2026-0420's 404 is treated as evidence rather than a bug; why the metric is called grounding_hit and not recall; and why this guide opens with the three places the brief it was written from disagreed with the repository. The discipline applies to the process too: the ADR-044 slice records two mistakes its implementer made and corrected — a timeout regression and a password printed into tool output — because leaving them out would have been the same kind of overclaim the project exists to avoid.

6.3 Databases: migrations first, then the scoped logins

Step 1 — apply every context's migrations with your own Windows login. Each *.Infrastructure project's design-time factory uses Trusted_Connection=True and creates its database if needed. The Infrastructure project must be both --project and --startup-project (verified on this machine: the host-as-startup form fails with "doesn't reference Microsoft.EntityFrameworkCore.Design"; this form prints "No migrations were applied. # PowerShell — all 17 contexts (7 physical databases)
$contexts = "AlarmManagement","ReactorFleet","CorePlatform","Instrumentation","DigitalTwin","Maintenance",
            "EventManagement","Robotics","RadiationMonitoring","EmergencyPreparedness","ReinforcementLearning",
            "Security","Organization","Audit","Compliance","Reporting","RootCause"
foreach ($c in $contexts) {
  $p = "src/Contexts/$c/Nexus1.$c.Infrastructure"
  dotnet ef database update --project $p --startup-project $p
}

Each context records its own history in dbo.__EFMigrationsHistory_<Context>. That is how eleven contexts share AlarmManagementDb without colliding (ADR-006, 020–026).

Step 2 — create the two scoped SQL logins, as your own sysadmin Windows login, using the T-SQL in the two runbooks (save each block as a .sql file and pass an absolute path to -i):

  • docs/runbooks/local-scoped-sql-login.md — nexus1_app: DML on exactly the schemas each database's contexts write, SELECT on dbo for the history tables, no DDL (ADR-028).
  • docs/runbooks/local-explain-readonly-sql-login.md — nexus1_explain: db_datareader on RootCauseDb plus explicit DENY on every write/execute verb (H7).

Choose your own local passwords where the runbooks show <your local … password>. They never go into a tracked file.

6.4 Connection strings in User Secrets

The hosts read their connection strings from each project's User Secrets store, which ASP.NET Core loads in the Development environment. The tracked appsettings.json files contain none, and an architecture test fails if a password is ever committed there (ADR-044).

# RootCause.Host — both logins
dotnet user-secrets set "ConnectionStrings:RootCauseDb" "Server=(localdb)\mssqllocaldb;Database=RootCauseDb;User Id=nexus1_app;Password=<your nexus1_app password>;" --project src/Hosts/Nexus1.RootCause.Host
dotnet user-secrets set "ConnectionStrings:RootCauseExplainDb" "Server=(localdb)\mssqllocaldb;Database=RootCauseDb;User Id=nexus1_explain;Password=<your nexus1_explain password>;" --project src/Hosts/Nexus1.RootCause.Host
# ModularRuntime and BFF — the same six keys each, all as nexus1_app
foreach ($h in "Nexus1.ModularRuntime","Nexus1.Bff") {
  foreach ($db in "AlarmManagementDb","AuditDb","ComplianceDb","ReportingDb","SecurityDb","OrganizationDb") {
    dotnet user-secrets set "ConnectionStrings:$db" "Server=(localdb)\mssqllocaldb;Database=$db;User Id=nexus1_app;Password=<your nexus1_app password>;" --project "src/Hosts/$h"
  }
}
dotnet user-secrets list --project src/Hosts/Nexus1.Bff     # check which keys a host has

The BFF also accepts an optional ConnectionStrings:RadiationMonitoringDb override; without it, RadiationMonitoring uses AlarmManagementDb. RabbitMQ's guest/guest development credentials remain in appsettings.json — out of ADR-044's scope.

History note. Earlier revisions committed the local development passwords in plaintext. ADR-044 moved them out of the tracked files without rotating them, so the old values remain in git history. Use your own values; never reuse the historical ones anywhere.

C · Glossary

AbstentionA run that ends without a verdict and with a named reason. A first-class outcome (HTTP 200), sealed like a verdict.
Attribution shareA candidate's weight: the share of the flood it newly explained in the greedy ranking (ADR-042). Not a probability.
Artefact edgeAn edge from a source that corrupts measurements (e.g. EMI from breaker BKR-2A) into the channels it couples into.
Backbone edgeAn engineered cascade edge with a delay window; walked and corroborated.
CoverageThe share of the flood's alarms a candidate's reach explains (FV-104: 11/14).
Fixed incidentA seeded, fully known teaching incident in IncidentRegistry (0418, 0419).
OnsetA channel's earliest good-quality historian sample — the physical start of its disturbance, as opposed to alarm arrival time.
One-Truth PipelineThe book's name for "the engine decides, the model explains", bounded by H1–H10.
Unexplained precursorAn alarmed component outside the origin's reach whose onset precedes the origin's (ADR-043).
Walking skeletonA thin but complete end-to-end implementation, proven before any breadth is added.
